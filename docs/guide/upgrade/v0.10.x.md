# Upgrade guide

<div class="preface">
This guide describes how to upgrade from <code>v0.9.x</code> to <code>v0.10.x</code>.
</div>

:::warning
Hybridly v0.10.x is still in beta, and breaking changes are still to be expected. It is not advised to upgrade right now.
:::

## Upgrade dependencies <impact-header impact="high" />

`v0.10.x` targets Laravel 13+ and Vite 8+.

## Update imports <impact-header impact="high" />

Many classes have changed their namespace. Update your imports accordingly:

- `Hybridly\View\Factory` is now `Hybridly\HybridResponseFactory`,
- `Hybridly\Support\Hybridable` is now `Hybridly\SerializesProperties`.
- All `Hybridly\Support\Property` classes are now in `Hybridly\`,
- All `Hybridly\Support\Configuration` classes are now in `Hybridly\Configuration\`,

## Update exception handling <impact-header impact="high" />

The `HandleHybridExceptions` class is no longer available to use in `bootstrap/app.php`. Instead, handle exceptions in a service provider:

```php
use Hybridly\Hybridly;
use Symfony\Component\HttpFoundation\Response;
use function Hybridly\view;

final class AppServiceProvider extends ServiceProvider
{
    public function boot(Hybridly $hybridly): void
    {
        $hybridly->renderExceptionsUsing(fn (Response $response) => view('error', [
            'status' => $response->getStatusCode(),
        ]));
    }
}
```

## Namespace changes <impact-header impact="high" />

- `Hybridly\Support\Hybridable` -> `Hybridly\Hybridable`

## Global middleware is now final <impact-header impact="high" />

## Flash data is no longer shared by default <impact-header impact="high" />

## Validation is now protocol-level <impact-header impact="high" />

Validation errors are no longer injected into `view.properties.errors`.
They now live in the protocol payload root under `validation`, grouped by error bag.

**Before**:

```json
{
	"view": {
		"properties": {
			"errors": {
				"email": "The email field is required."
			}
		}
	}
}
```

**After**:

```json
{
	"validation": {
		"default": {
			"email": "The email field is required."
		}
	}
}
```

If you were reading validation errors from global properties, migrate to protocol/context access:

```ts
import { useProperty } from 'hybridly/vue' // [!code --]
const errors = useProperty('errors') // [!code --]

import { useValidationBag } from 'hybridly/vue' // [!code ++]
const errors = useValidationBag() // [!code ++]
```

If you need full bag access:

```ts
import { useValidation } from 'hybridly/vue'

const validation = useValidation()
```

`useForm` keeps working as before. `errorBag` support is still available, and bags are now merged at the protocol level so multiple forms can coexist without colliding.

## Replace `partial` with `on_demand` <impact-header impact="high" />

The `partial` function was renamed to `on_demand`. Even if you grew used to it, the name was definitely confusing.

```php
use function Hybridly\partial; // [!code --]
use function Hybridly\on_demand; // [!code ++]

return hybridly('users.index', [
    'filters' => partial(fn () => $filters),  // [!code --]
    'filters' => on_demand(fn () => $filters),  // [!code ++]
]);
```

## Architecture API changes <impact-header impact="high" />

The `ComponentsResolver` interface was simplified:

- `loadModulesFrom` was removed.
- `loadComponentsFrom` was removed.
- `loadTypeScriptFilesFrom` was removed.
- `loadModuleFrom` now accepts only `directory` and `namespace`.

```php
$hybridly->loadModuleFrom(
    directory: __DIR__,
    namespace: 'billing',
    deep: true, // [!code --]
    loadViews: true, // [!code --]
    loadLayouts: true, // [!code --]
    loadComponents: true, // [!code --]
    loadTypeScript: true, // [!code --]
);
```

If you need fine-grained registration, use:

- `loadViewsFrom`
- `loadLayoutsFrom`
- `addView`
- `addLayout`

## Update refining filters <impact-header impact="high" />

The generic `Filters\Filter` class has been replaced by explicit filter classes.

```php
use Hybridly\Refining\Filters;

Filters\Filter::make('name');  // [!code --]
Filters\TextFilter::make('name');  // [!code ++]
Filters\NumericFilter::make('price');  // [!code ++]
Filters\DateFilter::make('published_at');  // [!code ++]
```

If you implemented custom filters, note that `Filter::apply` now receives a `QueryFilter` value object:

**Before**:

```php
public function apply(Builder $builder, mixed $value, string $property): void
{
    // ...
}
```

**After**:

```php
use Hybridly\Refining\Filters\QueryFilter;

public function apply(Builder $builder, QueryFilter $filter, string $property): void
{
    $value = $filter->value;
    // ...
}
```

## Update table payload usage <impact-header impact="high" />

Table records are now serialized as plain data objects. Cell-level rendered values and extras are no longer wrapped into each record field.

**Before**:

```json
{
	"records": [
		{
			"id": { "value": 1, "extra": [] },
			"name": { "value": "Ada Lovelace", "extra": { "class": "font-medium" } },
			"__hybridId": 1
		}
	]
}
```

**After**:

```json
{
	"keyName": "id",
	"records": [
		{ "id": 1, "name": "Ada" }
	],
	"cells": [
		{
			"key": 1,
			"columns": {
				"id": { "value": 1, "extra": [] },
				"name": { "value": "Ada Lovelace", "extra": { "class": "font-medium" } }
			}
		}
	]
}
```

If you were reading table records directly, update your code to use plain record values:

```ts
row.record.name.value // [!code --]
row.record.name // [!code ++]
```

When using `useTable`, continue using `value(column)` and `extra(column, path)` for rendered cell values and metadata:

```vue
<tr v-for="{ key, record, value, extra } in users.records" :key>
	<td>{{ record.name }}</td>
	<td>{{ value('name') }}</td>
	<td>{{ extra('name', 'class') }}</td>
</tr>
```

`__hybridId` has been removed. `useTable().records[*].key` is now only a local rendering key. Use `recordKey` when you need the server-identifiable record key, and check `hasKey` before rendering selection controls or server-side actions:

```vue
<tr v-for="{ key, recordKey, hasKey } in users.records" :key>
	<input v-if="hasKey" v-model="users.bindCheckbox(recordKey)" type="checkbox">
</tr>
```

Tables backed by data objects that do not expose a scalar model key now have `keyName: null`. They still render normally, but their inline actions, bulk actions and selection helpers are disabled. If a table needs actions or selection, include a scalar key such as `id` in the serialized data object.

For infinite scrolling or partial reloads that append table rows, replace generic table record merges with the table's `merge()` method. It keeps `records` and `cells` synchronized and deduplicates keyed rows:

```php
use function Hybridly\merge; // [!code --]

return view('users.index', [
    'users' => merge(fn () => UsersTable::make(), uniqueBy: 'id', path: 'records'), // [!code --]
    'users' => UsersTable::make()->merge(), // [!code ++]
]);
```

If you implemented a custom client adapter, update it to support the new `cells` payload, nullable `keyName`, and path-specific merge keys in the mergeable protocol metadata.

## Update custom mergeable properties <impact-header impact="medium" />

The `Hybridly\Mergeable` interface now includes `uniqueByPath()`. Custom mergeable property classes must implement it:

```php
public function uniqueByPath(): array
{
    return [];
}
```

## Updating `tsconfig.json` <impact-header impact="medium" />

The `tsconfig.json` auto-generated in `.hybridly` now expects the root `tsconfig.json` to be the following:

```json
{
	"files": [],
	"references": [
		{ "path": "./.hybridly/tsconfig.json" },
		{ "path": "./.hybridly/tsconfig.node.json" }
	]
}
```
